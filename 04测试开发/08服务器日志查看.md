# 日志查看关注事项

## 一、关键错误信息

日志中最需要优先关注的是直接暴露问题的异常标识，常见关键词包括：

- **错误类型**： **Error 、 Exception 、 Failed 、 Fatal 、 Crash 、 Panic**  等，这类关键词通常对应程序崩溃、功能失效等严重问题。
- **具体异常详情**：如 Java 的  NullPointerException 、Python 的  IndexError 、数据库的  Connection Refused  等，需记录异常堆栈（包含文件名、行号、调用链路），便于定位代码或配置问题。
- **错误码**：如 HTTP 5xx（服务器错误）、4xx（客户端错误）、数据库错误码（如 MySQL 的 1062 主键冲突），结合业务逻辑判断是否为预期内错误。

## 二、系统与资源告警

日志中常隐含系统资源瓶颈或配置异常，需关注：

- 资源超限： OutOfMemoryError （内存不足）、 Disk Full （磁盘满）、 CPU High （CPU 使用率过高）、 Network Timeout （网络超时）等，可能导致服务响应缓慢或宕机。
- 连接问题： Connection Timeout （连接超时）、 Connection Reset （连接被重置）、 Too Many Connections （数据库/服务连接数超限），需检查服务依赖（如数据库、缓存、第三方接口）是否可用。
- 权限问题： Permission Denied （文件/目录权限不足）、 Authentication Failed （认证失败），通常与配置文件权限、账号密码过期有关。

## 三、业务流程异常

从日志中**跟踪核心业务链路**是否正常，重点关注：

- 关键操作失败：如用户注册、订单支付、数据同步等核心流程的  Failed  日志，需确认是否影响用户体验或数据一致性（例如：“订单 12345 支付失败，原因：余额不足” 是预期内，但 “支付成功但订单状态未更新” 是严重异常）。
- 数据异常：如日志中出现空值（ null ）、负数金额、超出合理范围的数值（如订单金额 9999999 元），可能是业务逻辑漏洞或数据校验缺失。
- 频率异常：短时间内大量重复的错误日志（如 “接口 /api/login 连续 100 次返回 500”），可能是服务雪崩或恶意攻击的前兆。

## 四、实时动态与趋势

通过  tail -f  实时监控日志时，需观察：

- 日志输出频率：正常服务日志输出应平稳，若突然中断（长时间无新日志）可能服务已挂；若日志刷屏（如每秒数百行错误）可能触发了死循环或流量突增。
- 时间戳异常：日志时间戳是否与系统时间同步（避免因时区或时钟偏差导致的问题排查 confusion）；同一请求的日志时间间隔过长（如接口耗时超过 10s），需分析链路瓶颈。
- 重复模式：是否有周期性错误（如每小时出现一次数据库连接失败），可能与定时任务、资源回收机制有关。

## 五、安全相关日志

若涉及用户数据或敏感操作，需警惕：

- 恶意请求：日志中出现大量异常请求路径（如  /admin/xxx  未授权访问）、SQL 注入特征（如  ' or 1=1 -- ）、高频 IP 访问同一接口，可能是攻击行为。
- 敏感信息泄露：日志中是否意外打印密码、Token、身份证号等敏感数据，需立即整改日志输出规范。

## 六、查看日志的实用技巧

1. 结合工具过滤：用  **grep**  筛选关键词，例如：

  ```bash
  tail -f app.log | grep "Error"  # 只看错误日志
  tail -f app.log | grep -E "Error|Exception"  # 同时看 Error 和 Exception
  ```

  

2. 按时间范围筛选：若日志含**时间戳**（如  2025-07-24 10:00:00 ），用  

   ```bash
   grep "2025-07-24 10:0[0-5]" app.log  查看某 5 分钟内的日志。
   ```

3. 保存关键日志：遇到问题时，用  tee  保存实时日志到文件，避免退出后丢失：
tail -f app.log | grep "OrderFailed" | tee error_order.log


总结：**看日志的核心是“抓异常、追链路、联业务”**——先通过错误关键词定位问题现象，再结合上下文日志还原业务流程，最后关联系统资源和配置排查根本原因。日常可通过日志聚合工具（如 ELK、Grafana Loki）建立告警规则，提前发现潜在风险。
